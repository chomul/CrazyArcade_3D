# Checklist 34 — 봇 아이템 파밍 (`EBotState::SeekItem`)

> 2026-08-10 사용자 지적: "봇이 너무 싸우기만 하고 아이템을 먹고 강해질 생각을 일체 안 하는 것 같은데?"
> 회귀 스위트: `CrazyArcade3D.AI.BotSeekItem`

## 지적이 맞았다 (실측)
- [x] `EBotState` 에 아이템 관련 상태가 **아예 없었다** (`Wander`/`Attack`/`Evade`/`PopTrapped`)
- [x] 직전 판: 아이템 14개 노출 / 14개 획득 — **전부 지나가다 밟은 것**. 목표로 삼은 적이 한 번도 없다
- [x] 결과: 봇은 매치 내내 폭탄 1개·범위 1에 머문다. 사람이 아이템만 챙기면 후반이 일방적이 된다.
      크아에서 아이템 파밍이 게임의 절반인데 그 절반이 통째로 빠져 있었다

## 확정 방향 (사용자 선택: "가까이 있을 때만 줍기")
- [x] 몇 칸 이내의 **안전한** 아이템만 챙기고, 멀면 그냥 싸우거나 돌아다닌다
- [x] 초반에는 파괴 블록이 사방이라 6칸 안에 아이템이 자주 뜨고(자연스러운 파밍),
      후반에는 드물어 자연히 싸움이 중심이 된다 — **원한 흐름이 거리 상한 하나에서 나온다**

## 우선순위 `Evade > PopTrapped > 설치 > SeekItem > Attack > Wander`
- [x] **설치보다 아래**: 설치 분기는 이미 `ShouldPlaceBombAt(FootCell)` 을 통과한 뒤다 — 지금 서 있는
      자리가 놓을 자리다. 그 기회를 버리고 걸어가면 돌아왔을 때 그 자리는 대개 의미가 없다.
      결정적으로 **폭탄을 놓는 것이 곧 아이템을 만드는 행위**다(파괴 블록이 부서져야 아이템이 나온다) —
      설치를 미루면 파밍 총량 자체가 준다
- [x] **Attack 보다 위**: Attack 은 보상이 확정적이지 않은 먼 목표다. 어차피 이동 중이면 6걸음 이내
      아이템을 주워 가는 게 언제나 이득. 그리고 **Attack 에는 쿨다운이 없어 아래에 두면 거의 항상
      Attack 이 이겨 SeekItem 이 영영 발동하지 않는다** — 순서를 뒤집으면 안 되는 실질적 이유다
- [x] `EBotState` 에 **끝에 append** — 기존 값의 숫자가 바뀌면 재계획 진단 로그의 의미가 어긋난다

## 쓸모없는 아이템 거르기 — 넣었다
- [x] 이미 상한인 스탯을 주우러 6걸음을 걷는 것은 순수한 손해다. 판정 비용은 switch 하나
- [x] ⚠️ **판정을 봇이 아니라 `UStatusComponent::HasRoomForItem` 에 두고 `ServerApplyItem` 바로 옆에
      붙였다.** 클램프 조건이 두 파일로 갈라지면 "봇은 상한인 줄 아는데 실제로는 아직 오르는"
      어긋남이 조용히 생긴다. 각 `case` 가 `ServerApplyItem` 의 같은 `case` 와 1:1 이라 한쪽을 고치면
      다른 쪽이 눈에 들어온다
- [x] Roller 는 **상한 직전을 거르지 않는다** — `FMath::Min(Mul+Step, Cap)` 이 값을 바꾸기는 하므로
      여전히 이득이다 (테스트가 이 경계를 고정)
- [x] `default` 는 **`true` 가 안전측** — 새 아이템을 "쓸모없다" 고 단정해 영영 안 줍는 것보다
      한 번 가 보는 게 낫다
- [x] **가치 판단은 넣지 않았다** ("범위 vs 속도" 는 튜닝 지옥의 입구 — 범위 밖)

## 결정론 — 액터 순회를 아예 없앴다
- [x] `UExplosionSubsystem::GetActiveItemCellsSorted()` 추가 (`GetActiveBombCellsSorted` 와 같은
      좌표 사전순 규칙). 그 헤더에 이미 "액터 순회 순서는 판정 입력으로 부적합" 이라고 적혀 있다
- [x] **아이템은 셀이 곧 키**라 목표 확정도 `FindItemAt(Path.Last())` 로 끝난다 — 이 목표 경로에는
      액터 순회가 한 줄도 없다 (`PlanPopTrapped` 는 대상을 찾느라 한 번 훑어야 했다)
- [x] 고르는 아이템이 "그리드 + 출발 셀" 만으로 결정된다. 테스트가 **노출 순서를 뒤집어도** 확인

## 목표 상실 — 매 틱 확인한 것 / 안 한 것
- [x] 액터 소멸(남이 먼저 먹음·물줄기에 탐) · **목표 칸이 위험해짐** · 가는 도중 스탯이 상한에 닿음
- [x] 위험 판정은 `Tick` 이 이미 계산해 둔 `DangerCells` 를 받아 써서 조회 하나가 전부다.
      계속 가면 **도착하는 순간 물줄기와 만난다** — 실전에서 가장 비싼 실수
- [x] **도달 가능성은 매 틱 재확인하지 않는다** — 그건 매 틱 BFS 를 뜻하고 `BotReplanInterval` 이
      존재하는 이유가 정확히 그걸 막는 것이다. 재계획 주기(≤0.4초)와 `FollowPath` 의 경로 폐기
      가드가 잡는다
- [x] 평상시 비용: 노릴 아이템이 없으면 **BFS 이전에** 끝난다 (거리 프리필터는 수평 맨해튼 =
      경로 길이의 하한이라 갈 수 있는 목표를 잘못 버리지 않는다)

## 룰셋 — `BotSeekItemMaxCells = 6` (실제 걸음 수, 직선 아님)
| 근거 | |
|---|---|
| 6 ÷ `MoveSpeedCellsPerSec`(4) = **1.5초** | 폭탄 퓨즈(3초)의 절반 — "하나 줍고 제자리로 돌아올" 수 있는 거리 |
| 21×21 대각선 ≈ 40걸음의 **15%** | 화면 안, 눈앞 |
파밍이 소극적이면 8 → 10 으로 올리는 손잡이. **20 을 넘기면 "가까이" 가 아니다.**
