# FVoxelGrid

> `Source/CrazyArcade3D/Voxel/VoxelGrid.h` · 평범한 struct (UObject 아님)

지형의 **유일한 실체**. `FIntVector Size` + `TArray<uint8> Blocks`(X→Y→Z 평탄화)가 전부다.
블록은 이 게임에서 영원히 객체로 만들어지지 않는다 — 화면의 블록(HISM 인스턴스)은 이 배열을 보고 그린 **투영**이다.

## 왜 이렇게 했는가

### 왜 UObject가 아니라 평범한 struct인가
1. **값 복사가 자유롭다** — 테스트·맵 생성기가 그리드를 마음껏 만들고 버린다.
2. **순수 함수에 `const FVoxelGrid&`로 넘길 수 있다** — `Propagate`·`FMapValidator`·`VoxelMove`가 전부 이 형태.
   GC·리플리케이션·월드 같은 엔진 개념이 붙어 있으면 불가능하다.
3. 복제·권한 같은 "엔진과 얽히는 일"은 이 struct를 **소유한** `AVoxelWorld`(액터)가 맡는다.
   데이터와 액터의 역할 분리.

### 왜 셀이 struct/객체가 아니라 uint8 하나인가
- 셀에 실제로 필요한 정보는 **타입 하나뿐**이다. HP 없음(한 방에 부서짐),
  "누가 부쉈나" 없음(**있으면 안 됨** — Voxel이 게임 규칙을 알게 되는 순간 의존 규칙 붕괴),
  내장 아이템은 `AVoxelWorld::ItemPlacements` 별도 배열로 일부러 밖에 뺐다.
- 21×21×6 = 2,646셀 = **2.6KB** → L1 캐시에 통째로 들어간다. 이 배열은 "읽히는 횟수"가 다르다:
  봇 6마리가 매 틱 Propagate+BFS(최대 1024노드), 맵 생성 리롤마다 flood fill, 폭발 연쇄, 킥 정지 판정.
  전부 수천 셀 대량 조회 — 연속 바이트 배열이라 빠르고, 객체 참조 배열이면 셀마다 포인터를 쫓는다.
- **해시 검증이 공짜** — 1주차 마감 게이트(파괴 30건, 3인스턴스 해시 전부 일치)는
  지형 전체가 연속 바이트 버퍼라 CRC 한 번으로 끝났다.
- 타입 안전은 API 경계에서: 저장은 `uint8`, `Get/Set`은 `EBlockType`(enum class)로 주고받는다.

### 왜 3차원 중첩 배열이 아니라 1차원 평탄화인가
- `TArray<TArray<TArray<>>>`는 층마다 별도 할당·포인터 간접 참조로 캐시에 적대적이고,
  UE에서는 중첩 컨테이너를 `UPROPERTY`로 못 쓴다.
- 평탄화(`Index = X + Y*W + Z*W*H`)는 할당 한 번, 연속 메모리,
  **순회 순서가 코드에 명시적** — 맵 생성 결정론(불변식 4)과 맞물린다.

### dense/sparse 분할 — 이 프로젝트 설계의 기본기
```
빽빽한 것(dense) = 배열          듬성한 것(sparse) = 액터
지형 2,646셀 → FVoxelGrid       폭탄 최대 ~40개 → ABomb
                                노출된 아이템 몇 개 → AItemPickup
```
개별 상태·타이머·복제가 진짜 필요한 소수만 액터. 지형처럼 개수가 많고 셀당 정보가 작으면 배열.
마인크래프트도 청크 = 압축 배열이지 블록 = 객체가 아니다.

## 핵심 API
- `Init(Size)` / `IsValid(Cell)` / `Index(Cell)` / `Get(Cell)`(범위 밖 = Empty) / `Set(Cell, Type)`
- `IsSolid(Cell)` / `BlocksExplosion(Cell)`(Immortal만 true)
- 복제·RPC 없음 — 전부 소유자 `AVoxelWorld` 소관

## Q&A

**Q. 블록들을 만들기 전에 현재 그리드의 배열을 가지고 있는 구조체라고 보면 되나?**
절반만 맞다. "배열을 가진 구조체"는 맞지만 "만들기 전"이 틀렸다 — 블록은 이후에도 객체로
만들어지지 않는다. 이 배열이 **매치 내내 지형 그 자체**이고, 파괴 = `Set(Cell, Empty)` 한 줄이다.
HISM 인스턴스 제거는 그 뒤를 따라오는 표시 갱신일 뿐. 모든 판정(폭발 전파·봇 BFS·킥 정지·발밑 셀)이
화면의 블록이 아니라 이 구조체를 직접 읽는다 — 그래서 "보이는 것"과 "판정"이 어긋날 수 없다.

**Q. 보통은 Grid(셀) 객체를 하나 만들고 그걸 배열로 가지지 않나? 왜 uint8 배열인가?**
셀이 풍부한 개별 상태·행동을 가질 때는 그 방식이 맞다(타워 디펜스 타일 등). 여기 셀은 정보가
정확히 1바이트(타입)뿐이고, 대량 조회가 매 틱 돌므로 캐시 친화적인 연속 배열이 압도적으로 유리하다.
위 "왜 셀이 uint8 하나인가" · "dense/sparse 분할" 참조.
