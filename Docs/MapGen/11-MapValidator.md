# FMapValidator

> `Source/CrazyArcade3D/MapGen/MapValidator.h/.cpp` · 전부 static 순수 함수

GDD 4.2의 맵 검증 5종: ① 스폰 연결성 ② 스폰 최소 거리(맨해튼) ③ 스폰 탈출로
④ 고립 구역 없음 ⑤ 아이템 사분면 균등. `Validate`가 리롤 판정의 관문.

## 역할

- 생성된 맵이 **플레이 가능한지 판정**한다 — 리롤 루프의 관문.
- 검증 5종: ① 스폰 전원 연결 ② 스폰 간 최소 거리 ③ 스폰별 탈출로 ④ 고립 구역 없음
  ⑤ 아이템 사분면 균등. 실패 사유를 문자열로 보고한다(리롤 로그).

## 왜 이렇게 했는가

- **왜 순수 함수인가** — 생성기의 리롤 루프 안에서 수십 번 불린다. 상태가 있으면
  호출 순서가 결과에 영향을 줄 수 있고, 결정론이 깨진다. `const FVoxelGrid&`만 받는다.
- **이동 그래프가 곧 게임 규칙** — "도달 가능"의 정의는 `VoxelMove`(1칸은 오르고 2칸은
  못 오름, 낙하 무제한)를 그대로 쓴다. 검증기가 자체 이동 규칙을 들면 봇과 갈라진다 —
  실제로 그랬고, 그래서 `VoxelMove`로 통일됐다.
- **⚠️ ④(고립 구역)는 최외곽 링을 제외한다** — 경계 벽 꼭대기는 도달 불가가 **설계**다
  (1칸 점프로 벽 위에 못 올라가게 2층으로 올린 것). 제외하지 않으면 정상 맵이 전부
  불통과라 리롤이 무한히 돈다. 첫 구현에서 실제로 폴백 맵이 불통과했다 —
  "검증 규칙에도 게임 디자인 의도가 들어간다"는 사례.
- **실행 순서는 번호순이 아니라 비용순** — ②(거리 비교) → ③(6방향 검사) → ⑤(카운트)
  → ①·④(BFS/flood fill). 리롤 루프 안이므로 싼 검사로 먼저 걸러 비싼 검사를 아낀다.
- **flood fill이 TArray 큐인 이유** — TQueue·TSet 순회는 순서 보장이 약하다.
  결정론 유지를 위해 컨테이너도 TArray로 고정(불변식 4).
- **임계값의 근거가 실측** — 폴백 맵의 스폰 간 최소 맨해튼이 9 → 임계값 8.
  "이미 좋다고 검증된 맵이 통과하는 선"에서 출발했다.
